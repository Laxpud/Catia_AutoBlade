# 内置翼型目录

内置翼型目录是 wheel 中经过来源和再分发审计的只读数据集合。它与源码仓库的维护者回归输入分离，用户只有显式执行 `autoblade init --with-airfoil-library` 时才会把完整目录复制到包外工作区。

## 当前内容

首版目录包含 Hannnk 直接授权再分发的三个尖后缘翼型：

| 稳定 ID | 点数 | 分发状态 |
| --- | ---: | --- |
| `airfoil1_sharp` | 300 | 已审计，纳入清单 |
| `airfoil2_sharp` | 253 | 已审计，纳入清单 |
| `airfoil3_sharp` | 249 | 已审计，纳入清单 |

作者、授权方式、项目内修改和 SHA-256 记录在包资源 `autoblade/resources/airfoil_library/manifest.json`；人类可读的授权及脱敏说明见[真实示例数据审计](example-data-audit.md)。清单摘要针对 `.gitattributes` 固定为 LF 的实际分发字节。

以下仓库输入不属于当前内置目录：

- `sc1095.csv`、`sc1095_sharp.csv`、`sd7032_sharp.csv` 和 `naca0012_sharp.csv` 尚无本轮可核验的来源与再分发授权，只保留为源码回归资产；
- `airfoil1_sharp_dense_1000.csv` 是密集点云历史缺陷回归资产，不进入最短用户数据路径；
- 来源、授权或用途边界不明确的文件不得因为已经存在于 `input/` 就自动进入 wheel 目录。

## 初始化语义

```powershell
autoblade init C:\Engineering\blade-workspace --with-airfoil-library
```

该选项复制清单、清单内全部 CSV 和基础工作区，不复制任何截面示例。`--with-examples` 只复制真实 89 截面示例及其三个依赖翼型，不复制目录清单。两个选项可以同时使用；目标相同的翼型只计划一次。

初始化器在写盘前读取清单，校验 schema、规范文件名、重复项和每份 CSV 的 SHA-256。已存在的清单或翼型与其他受管理文件一样需要 `--force` 或交互确认；目标中的无关用户文件不会被删除。

包管理器只拥有 `site-packages` 内的不可变资源。复制后的 `input/airfoils/` 属于用户工作区，安装、升级或卸载 wheel 都不会调用 `init`，也不会移动、覆盖或删除这些外部数据。

## 清单变更门槛

新增或修改翼型必须同时完成以下工作：

1. 为每个稳定 ID 记录作者、来源主页、标准许可证或直接再分发授权；
2. 记录是否修改、修改说明、点数和实际分发字节的 SHA-256；
3. 通过 CSV 数据校验，并证明仓库参考输入与包资源的记录内容一致；
4. 更新 wheel 内容白名单、安装冒烟、工作区覆盖保护和发布说明；
5. 修改坐标、点序或后缘拓扑时补做对应真实 CATIA 回归。

标准许可证和作者直接授权都是可接受的依据；仅有公开下载地址、常见翼型名称或仓库历史不构成再分发授权。

## 版本与拆包边界

短期内目录与 `autoblade` wheel 同版本发布，不建立独立的目录版本号。`manifest.json` 的 `schema_version` 只表示清单结构，不能解释为数据内容版本；某个软件版本的目录内容由该版本 wheel、清单中的精确文件集合和每文件 SHA-256 共同确定。

初始化器和自动化测试同时检查“清单中的文件都存在”和“包中的 CSV 都进入清单”，因此同一发布制品不会包含未审计的隐藏翼型。增加、修改或删除任一条目都属于软件发布内容变化，必须更新未发布说明，随后进入下一个版本的正式 Release Notes，并重新执行完整分发检查。

只有满足以下任一条件时才评估拆为独立数据包：

- 翼型数据的更新节奏明显独立于程序版本；
- 点云数量或 wheel 体积显著增长，给代码安装和升级造成实际负担；
- 某些数据许可证、授权撤回或分发渠道要求把数据与 MIT 代码隔离。

在触发条件出现前不创建空数据包、下载器或第二套版本解析逻辑。未来若拆包，必须先设计旧 wheel、外部工作区、离线安装和清单验证的兼容迁移，不能让升级或卸载接管已经复制的用户数据。
